> 术语与命名见 [0008](0008-命名-标注与圈批Diple.md)：「摘录」现称「标注」，插件现名「圈批 · Diple」。

# 交接协议：带代次的认领、稳定批次、单调终态、后端推导 settled

补充 ADR 0004（事件约定）和 design §4。R1–R3 三轮审查里，交接（审阅 → 摘录：handoff → claim → 发送 → receipt → batch.sent → settled）每轮都在新的时序下出问题（XE-04、XE2-03、XE3-01/02、XR-09、XR3-01…04）。原因是两个插件各自打补丁，没有一份两端共同遵守的规则。本 ADR 就是这份规则。规则的纯逻辑部分放在 `packages/core/src/handoff-protocol.js`，两个插件共用：

- `ledgerStep`：「摘录」后端一条认领记录的状态机。Python 的 `ExcerptStore` 是它的 SQLite 版本，两边跑同一份用例表 `packages/core/test/handoff-ledger.cases.json`。
- `receiverStep`：「摘录」前端一个窗口处理一次交接的状态机。适配器是 `send/handoff.js`。
- `senderStep`：「审阅」前端一次交接从发出到定稿的状态机。适配器是 `review/handoff.js`。

三个状态机都写成 `step(state, event) → { state, effects }` 的形式，调用方只负责执行副作用，再把结果作为事件送回去。

## 1. 认领：持有者 token + 代次，所有推进都做 CAS

- 认领记录的字段是 `owner`、`generation`、`batchId`、`stage`（claimed → added → sending，只能往前走）、`accepted`、`receipt`、`settled`、`at`（租约时间）。
- `claim {owner, batchId}` 有四种结果：
  - 没有记录：建一条记录，`generation = 1`，返回 `{claimed:true, owner, generation, batchId}`。
  - 已有 receipt 或 settled：返回 `{claimed:false, receipt?, settled?}`。
  - 租约过期（`now - at > 30 s`）且还没有 receipt：接手。`generation + 1`，换成新的 owner，返回原有的 `batchId` 和进度 `progress`。
  - 其他情况：返回 `{claimed:false}`。
- `advance {owner, generation, stage, accepted}` 和 `receipt {owner, generation, …}` 都是比较后写入，条件是 `WHERE owner = ? AND generation = ?`，并且还没有 receipt（advance 还要求没有 settled）。更新了 0 行，后端返回 **409 `lost-claim`**；前端收到 409 立刻停下，不再 add、不再 submit、不再发回执。每次 CAS 成功都会续租。
- 前端在执行没有 fence 保护的副作用（把条目加进列表）之前，要确认租约是新鲜的：从发出 claim 请求算起不超过 15 s（租约的一半）。超过了就先做一次 advance 心跳，返回 409 就停。R3 复现的「claim 响应迟到 31 s」就是在这一步被挡住的。

## 2. 批次号在认领时确定

- 第一次认领时，前端提议一个批次号，后端存下来。之后每次认领、接手，返回的都是这个批次号，这次交接只会用这个号发送。
- `put_batch` 拒绝重新登记已经有终态（`outcome`）的批次，已展开的批次照旧拒绝。所以旧持有者就算绕过了 CAS，也不能用同一个号再发一次，更不可能生成第二个批次。

## 3. 终态单调

- 「摘录」后端有两层终态：
  - 批次的 `outcome`（delivered | failed）。
  - 每个交接的 `settled`。
  
  两者都只在为空时写入，第一次写入的值有效，之后不会再被改写。
- 「审阅」后端：
  - 真实的 settled 写入后，迟到的 `batch.sent` 不能再把这批条目改成 sent（XR3-01 A）。
  - 迟到的 receipt 只存下来，不再改条目的 queued，也不会让条目重新进入「等待确认」（XR3-01 B）。
  - 只有推断出来的结论（`inferred`）可以被真实的 settled 覆盖。
  - 对方声明了 `settles:true` 时，后端不接受推断结论。

## 4. settled 的送达：前端发件箱 + 后端推导

- 发送流程在清理发送事务之前（删 inflight、`confirm.*`、恢复列表之前），先把最终结果同步写进前端发件箱 `final.<batchId> = {delivered, reason?, handoffIds}`（ctx.storage）。然后 `POST /batches/{id}/final`；失败就按退避重试，`resume()` 和 `reconnected()` 也会再冲一次，2xx 之后才删掉这条记录。
- 后端在一个事务里完成三件事：写批次的 `outcome`（单调）、关联 `batch_handoffs`、为每个交接写 `settled`（单调）。然后逐个广播 `handoff.settled`。
- 查询的时候由后端推导：claim、`POST /handoff/{id}/replay`、`GET /handoff/{id}` 遇到有 receipt 但没有 settled 的交接时，会从关联批次的 `outcome`（或 `answered` 状态）推导出 settled 并存下来。所以重播、重连、换窗口都能补发，不依赖前端那一次请求。
- 接收方无论是「本窗口处理过」还是「别的窗口处理完」，收到重播的交接都调 `replay` 路由，由后端重放已存的 receipt 和推导出的 settled（XR3-02：同一个窗口也能补发）。

## 5. 一个批次对应多个交接

- 队列条目保存 `handoffIds[]`，同一会话多次 sendNow 排队时追加，不覆盖。本地批次记录和 `PUT /batches`（`handoffIds`）都带上这个列表。成功、失败、取消、重载后判为 lost，都对列表里的每个交接写一条终态（XE3-02 / XR3-03）。
- 「审阅」后端按交接 → 条目（receipt.accepted）分别结算。

### 5.1 结算看批次里实际有什么（fix-r4，R4 XE4-02）

- 一个交接被接受，不等于它的条目一定随批次发出：排队期间用户可能把它从待发列表删掉，或者被另一次交接换成了新版本。所以交接的结论只看**实际进入批次的条目**。
- 「摘录」前端在 `PUT /batches/{id}` 里带上可选字段 `handoffItems: {handoffId: [{itemId, revision}]}`，即每个交接接受了哪些条目的哪个版本。后端存进 `batch_handoffs.accepted_json`。旧前端不带这个字段时，退回到回执或进度里的 `accepted`（只有 itemId，不比较版本）。
- 结算规则是共享核心的 `settledForHandoff(batch, handoffId, accepted)`，Python 侧是 `store.settled_for_handoff`，两边跑同一份用例表 `packages/core/test/handoff-settle.cases.json`：
  - 接受的条目全部在批次里（同一个 itemId；已知版本时还要同一个 revision）：照批次的结论，载荷和以前一样。
  - 一条都不在：`delivered:false`，reason 为 `removed`（批次里没有这个 itemId）或 `replaced`（批次里是另一个版本）。不管批次本身是成功、失败还是取消，都不会报「已发送」。
  - 部分在：`delivered` 照批次，并附 `items:[{itemId, delivered, reason?}]` 说明哪些发了、哪些没发。
  - 不知道成员的情况（没有 accepted，或者批次从没登记过，比如排队时就被取消、`/final` 补写的占位行），仍按批次的结论处理整个交接。
  - fix-r5（XE4-02 残余）：**登记过的批次，成员一定已知**。`put_batch` 收到的就是批次的完整条目，即使里面一条交接条目都没有（只有手动摘录，或者没有条目），也算「已知不含」，交接结算为 `removed`、`delivered:false`。共享函数里 `batch.items` 是数组就表示已登记，`null`/缺省表示没登记。后端用 `batches.members_known` 区分：R5 之后 `put_batch` 写的行为 1；R5 之前的行只有在关联上声明过 `handoffItems`、或条目里带了交接 itemId 时才算已知，否则按旧规则（批次的结论），保证升级前的数据不被改判。
- `handoff.settled` 载荷新增可选字段 `items`，只在不是全部条目都发出时出现。旧版「审阅」忽略它，只看 `delivered`。新版「审阅」后端只把 `delivered:true` 的条目标为已发送；`removed` / `replaced` 的条目回到待发，并且不再记为「在某个会话的待发列表里」；其余失败条目照旧放回待发列表。审阅页的提示只计实际发出的条目。

- fix-r5（XE5-02）：**能力协商**。`items` 只告诉声明过能读它的对端。「审阅」发出的 handoff 载荷带 `caps:['partial']`；「摘录」接收方认领时把 caps 交给后端（`POST /handoff/{id}/claim` 的 `caps`，存进 `handoff_claims.caps_json`）。后端每次对外给出 settled（广播 `handoff.settled`、`/final`、claim、replay、`GET /handoff/{id}` 的响应）都先过一遍共享函数 `settledForPeer(settled, caps)`：
  - 对端声明了 `partial`：原样给出，部分结算时顶层 `delivered:true` 加分项 `items`。
  - 没声明（R5 之前的「审阅」）：去掉 `items`；如果是部分结算（`delivered:true` 但有条目没发出），改成 `delivered:false, reason:'partial'`。旧版审阅端会把这个交接的条目全部退回待发：用户可能要重发一次已经发出的条目，但绝不会看到没发出的条目显示为已发送。
  - 存下来的 settled 不变，只改线上给出的那份。
- 审阅端按分项只把真正发出的条目计为已发送（共享函数 `itemOutcomes`；Python 侧 `item_outcomes`）。settled 比 receipt 先到时，receipt 给出的结果同样按分项收窄。对端是从不 settle 的旧版「摘录」时，只按 `batch.sent` / `batch.answered` 里实际带着的条目计已发送。
- **共享决策函数的双实现**：`settledFromBatch`、`settledForHandoff`、`settledForPeer`（摘录后端）和 `itemOutcomes`（审阅后端）都有 Python 孪生实现。除了共享用例表 `handoff-settle.cases.json`、`handoff-peer.cases.json`，还有差分测试：`packages/core/test/protocol-diff.mjs` 生成随机输入（含畸形值：非字符串 id、非整数 revision、缺字段、超长和多字节 reason），`tests/python/test_protocol_diff.py` 断言 Python 输出与 JS 完全相同；`ledgerStep` 也用随机请求序列对 SQLite 实现做同样的比较。约定：id 只认字符串，revision 只认整数，reason 截到 100 个码点。

### 5.2 一个批次只有一个首个终态（补充 §3，fix-r4）

- 后端的批次终态以第一次为准，跨层也一样：`mark_answered` 在批次变为 `answered` 的同一刻把 `outcome` 固定为 `delivered`；从 `answered` 推导 settled 时，如果 `outcome` 还空着，也会一起写入。之后再来的相反 `/final` 不会改写 `outcome`，也不会改写已经存下的 settled。它会拿回已有的终态，响应里带 `conflict:true`。
- 迁移时（每次打开库都会做，幂等）还会把旧认领补进 `batch_handoffs`：批次号来自 `receipt.batchId`、`progress.batchId` 或认领的 `batch_id`（XE4-03）。这样 R3 之前的回执也能从批次推导出 settled。

### 5.3 出处只绑定事件到达前就已存在的捕获（fix-r5，R5 XE5-01）

- 这不是交接协议本身，但是同一类问题（异步处理时去读「当前」列表），规则记在这里。
- 捕获的那一刻同步记下 `bind.after`（此前到达的最后一个 `message.complete` 的序号）和 `bind.rt`（该会话当时运行的 runtime id，未知为 null）。
- `message.complete` 到达时同步记进完成轮次账本（`capture/turns.js`），并同步决定、固定所有已能确定的捕获。一个捕获只属于 `after` 之后**第一个**属于它会话的完成轮次：已知会话的轮次直接比较；runtime 还没映射的轮次，若 rid 等于捕获时的 `rt` 就是它的，`rt` 已知而 rid 不同就不是它的，`rt` 未知则这个捕获先挂起（只挂起它，不挡其他会话）。
- 未知 runtime 由一次有超时（`RESOLVE_TIMEOUT_MS`）的 `session.active_list` 查询映射；映射回来也只按账本判断，所以只会处理事件到达时就已存在的捕获。超时或查不到，挂起的捕获保持未验证；之后才得知的配对（比如用户聚焦了那个会话）仍按原来的到达顺序判断。
- 测试在 `register(ctx)` 入口上做（`tests/desktop/capture-r5.test.mjs`）：T1 complete、T2 capture、T2 complete 固定顺序，插入无关会话 complete、映射返回、历史读取失败三种事件的全部 120 种位置 × runtime 已知/未知 × 映射成功/为空，共 480 种，断言每条出处要么验证到自己那一轮的行，要么保持未验证。

## 6. 审阅端什么时候可以推断

- 新版「摘录」在 receipt 里声明 `settles:true`。这时审阅端只认 settled，不从 `batch.sent`、`batch.answered` 推断。等待期间按退避用 `{settle:true}` 重播交接，主动去拉结果（15 s、30 s、60 s…，最长 5 分钟一次）。超时只显示「未知」，之后可以被更正。
- receipt 里没有 `settles` 的旧版接收方，沿用 R2 的推断：`batch.answered` 算已送达；`batch.sent` 之后 60 s 没有其他消息也算已送达。推断结论带 `inferred` 标记。
- 已经显示了推断的「已发送」或「未知」，之后收到真实的 settled 且结论不同时，更正提示并刷新清单（XR3-04）；结论相同就不再提示。
- fix-r6（R6 XE6-01）：**推断出的结论，提示和写入是同一份**。推断由状态机 `senderStep` 自己算出：`sent` / `answered` 事件带 `carried`（批次事件里实际带着的交接条目，多次事件取并集），推断时按它逐项给结论，没带着的条目是 `{delivered:false, reason:'removed'}`，不套用批次的结论。`final` 和 `record` 两个副作用都带这同一份 `items`：部分带着时顶层 `delivered:true` 加 `items`；一条都没带着时 `delivered:false, reason:'removed'` 加 `items`；全部带着或不知道成员（事件没列条目）时仍是整个交接 `delivered:true`、不带 `items`。适配层把 `record` 原样写进 `POST /handoffs/{id}/settled`（带 `inferred`、`reason`、`items`），审阅后端按 §5.1 的分项规则只把带着的条目标为已发送。`batch.answered` 和 `batch.sent` + 60 s 两条推断路径相同。

## 不变量（时序排列测试断言）

1. 同一个 handoffId 最多提交一次：多个窗口并发认领、响应延迟或丢失、租约接手、重复广播，都不会产生第二次 `submit`，也不会出现第二个批次号。
2. 失败不会显示为成功：真实结果是失败时，对方声明 `settles:true` 的情况下，任何时刻都不会显示「已发送」；收齐事件后，最终显示的一定是「退回」。旧版对方的推断成功，在真实失败到达后会被更正。

## Consequences

- 「摘录」库新增列 `handoff_claims.owner / generation / batch_id`、`batches.outcome / outcome_reason`，以及新表 `batch_handoffs`。迁移沿用 `BEGIN IMMEDIATE`。旧记录的 `generation` 为 0、`owner` 为空，不能用 CAS 推进，只能等租约过期后被接手，或者被重放。
- `/events/handoff-receipt` 现在必须带 `owner` 和 `generation`。`/events/handoff-settled` 保留，内部改走同一套单调写入。
- 事件载荷仍是 v1，只新增了可选字段 `settles`。两个插件都继续兼容不带这个字段的对方。
- fix-r6：审阅端写入的推断结论（`/handoffs/{id}/settled`，`inferred` 非空）可能带 `items` 和 `reason:'removed'`；审阅后端早已接受这两个字段，库结构不变。
- fix-r5：`handoff_claims.caps_json`、`batches.members_known` 两列（迁移补列）；handoff 载荷可选 `caps`，claim 请求可选 `caps`；对未声明 `partial` 的对端，部分结算以 `delivered:false, reason:'partial'` 给出。已知限制：旧版审阅端遇到部分结算会把已发出的条目也退回待发，用户可能重复发送。
- fix-r4：`batch_handoffs.accepted_json` 列（迁移补列）；`PUT /batches` 增加可选 `handoffItems`；`handoff.settled` 和 `/batches/{id}/final` 的 `settled` 可能带 `items`；`/final` 响应可能带 `conflict:true`。以上都是可选字段，旧版对方不受影响。
