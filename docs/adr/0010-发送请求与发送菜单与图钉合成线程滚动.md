# 发送请求（SendRequest）、共享发送菜单（SendMenu），以及图钉由合成线程跟随滚动

出处：V2.1 用户实机验收反馈第 5 项（图钉位置和卡顿）、第 8 项（发送参考 Orca）。ADR 0009 定了 desktop-kit 和发送接口按角色收口；本篇在它之上新增两个共享模块和一套图钉定位方案。**发送引擎一行没改**：交接协议（ADR 0007）、BatchCatalog、sending 的角色接口和它们的不变量（不丢意见、不发错会话、不重复发、不虚报已发送）都保持原样，新界面只通过现有接口发起请求。

## 决定

### 1. `@diple/core` 的 `SendRequest`：范围 + 目标 → 一次发送请求

一个纯函数，两个插件的发送菜单共用。它只负责**描述**请求，不负责执行：聊天版交给 `sending.request` 执行（ADR 0009），文档版交给 `handoff.send` 执行。

```
SendRequest.plan({ scope, target, items, focusedSessionId, explicit })
  scope:  { kind: 'item', id } | { kind: 'unsent' }
  target: { kind: 'session', sessionId }   立刻发到这个会话
        | { kind: 'queue' }                加入待发：当前会话的待发列表，不发
        | { kind: 'copy' }                 复制给 AI：什么都不发
        | { kind: 'new' }                  新会话：SDK 做不到 → 拒绝（unsupported-target）
  → { ok, kind: 'send', sessionId, sendNow, itemIds, confirm } | { ok, kind: 'copy', itemIds } | { ok: false, reason }
SendRequest.targets({ current, recent }) → 当前会话、最多 5 个最近会话（去重）、加入待发
```

- `confirm` 表示是否要先问一句「发到「某某」吗」。只有两个条件同时满足时才为真：用户没有亲手选目标（比如通过快捷键发送），并且目标不是当前聚焦的会话（design §2.10b）。用户在菜单里亲手选了目标（`explicit`），就不再确认，选择本身就是答复。
- 「哪些算未发送」由调用方决定（`items[].unsent`）。纯函数不关心状态机。

### 2. `@diple/desktop-kit` 的 `SendMenu`：两边行为相同的那部分菜单

`<SendMenu label sections onClose attrs />`。sections 由若干分区组成：要选的范围（单选项，选完菜单不关）、要发往的目标、复制操作。两边共享的只是**行为**（D1 §L7）：键盘操作（↑ ↓ Home End、Enter / Space）、焦点（默认落在标了 default 的目标上）、关闭方式（Esc、Tab、点外面、选中目标）、role=menu 和 menuitem / menuitemradio。分区里放什么由各插件自己决定：

- 聊天版：胶囊条的「发送 N 条 ▾」只放「直接发送」和「复制给 AI」两项，目标固定为当前会话，没有目标列表。主路径不变：在输入框写自己的话，回车，标注随消息一起发出。
- 文档版（完全照 Orca 的做法）：清单顶部的「发送 N 条 ▾」和每张卡片上的「发送这一条」打开的是同一个菜单。范围有「这一条」和「本文件全部未发送」两项；目标依次是当前会话（默认）、最近的会话（最多 5 个）、加入聊天待发；最后是复制给 AI。原来卡片上的「加入待发」「直接发送」两个按钮已删除。

位置：默认绝对定位，挂在触发按钮的末端边缘下方，下方放不下就翻到上方。如果某个会裁剪内容的祖先元素（比如文档清单的滚动区）上下都放不下菜单，菜单就改成 `position: fixed`，贴着触发按钮、留在窗口内（`data-fixed`），并且在那个祖先滚动时关闭。这一条是在真机上发现的：清单里位置靠下的卡片，菜单会被滚动区裁掉。

文档版的执行路径：`page.sendItems(picked, { sessionId, sendNow })`。它先保存还在编辑中的意见，再调用 `handoff.send`。`handoff.send` 本来就接受 `sessionId`，**所以接口不需要新增参数**。连点保护（`sending.current`、`busy`）原样保留：保存过程中连点、或者在同一个事件循环里连点两次菜单项，都只会发出一次交接（XV9-02，有测试）。

### 3. 不做「新会话」目标

Hermes 桌面端 SDK 的 `host.newChat()` 只会开一个草稿，不返回已存储的会话 id，交接协议因此没有可投递的目标。我们不绕过 SDK，`SendRequest` 遇到 `new` 目标直接拒绝。这一条已写进已知限制和 ROADMAP，状态是 blocked，等宿主提供接口。

### 4. 图钉：只在必要时测量，滚动交给合成线程

图钉骑在选区的右上角（Codex 的做法，`capture/pins/layout.js` 是纯函数）。成本模型：

- **测量**（`getClientRects` 和视口的 rect）只在文字可能发生非滚动移动时进行：resize、视口或内容尺寸变化（ResizeObserver）、字体加载完成、图钉集合或状态变化、切回聊天标签页。这些触发合并成一次，放在本帧布局完成之后执行（借助一个探针元素的 ResizeObserver 回调），所以读取时不会强制布局。只测量位于屏幕上或附近的消息里的图钉（IntersectionObserver，上下各留一屏余量）。
- **滚动时不运行我们的脚本**：每个视口的一组图钉由一个滚动驱动动画移动（在该视口上建 ScrollTimeline，做一次 translate3d）。滚动过程中如果有测量请求，就等滚动停下（约 140ms）再做。
- 没有 ScrollTimeline 的宿主或 jsdom：在捕获阶段监听 scroll 事件，记下位置，在一个 rAF 里每组只写一次 translate3d；图钉是否可见用算术判断（`visibleAt`）。全程不改 left 和 top。
- 重叠的图钉在一次线性扫描中横向错开，不需要两两比较，也不需要重新测量。

实测（`tests/e2e/v21-pin-perf.mjs`，160 条消息、30 个图钉，同一沙箱下修复前后对比）：

| | 修复前 | 修复后 |
|---|---|---|
| 每帧脚本耗时中位数 | 0.108 ms | 0.016 ms |
| p95 | 9.569 ms | 2.009 ms |
| 我们代码引起的强制布局次数 | 99 | 0 |
| 我们代码引起的 long task | 4 | 0 |
| 停止滚动后与原文的偏差 | 50.18 px（旧的页边规则） | 0.62 px |

阈值（中位数 < 1ms、p95 < 4ms、无强制布局、无 >50ms 的 long task、偏差 ≤ 1px）只在 `PERF=1` 时强制检查，平时只打印数字。

## 后果

- 两个插件的「选什么、发到哪」只有一个出处（`SendRequest`），菜单交互也只有一个出处（`SendMenu`），两边不会各自漂移。
- 文档版的跨会话发送不再需要二次确认。确认逻辑留在 `SendRequest` 里，供以后没有显式选择目标的入口（比如快捷键）使用。
- 图钉的滚动性能依赖宿主 Chromium 的 ScrollTimeline；没有时退回 rAF，行为一致，只是滚动帧里会多出少量脚本。
- 使用界面不显示快捷键键帽（守卫测试 `v21-no-keycaps`），快捷键的教学留给以后的 onboarding（ROADMAP）。
